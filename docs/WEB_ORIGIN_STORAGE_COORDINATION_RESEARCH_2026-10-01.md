# W11：同来源 Web 存储协调与实际反例

研究日期：2026-10-01。问题是两个独立页面能否保留各自新增记录，并拒绝已经失效的修改及恢复预览。所有浏览器操作使用隔离本机来源和固定合成数据；没有访问真实账户、导出或远端数据库。

## 独立预期与旧实现

先冻结独立预期，再构建旧实现探针。在两个实际页面都已缓存空状态时，页面 A 新增 A、页面 B 新增 B，重新读取后只剩 B。重建 A 后，两个页面预备同一记录的不同修改，两次提交都被接受，页面 B 覆盖页面 A，首个修改的历史也丢失。这是实际 SharedPreferences Web 行为，区别于进程内 mock 测试。

原始观测、旧工具原文、构建身份与失败仍在本地忽略路径 `build/mega_upgrade/w11_two_tab_research/`，未通过重写旧结果掩盖反例。

## 协议及来源

依据 [W3C Web Locks 工作草案](https://www.w3.org/TR/2025/WD-web-locks-20250924/)，同一存储来源的参与方可以用同名排他锁协调异步工作。此 API 是合作协议，并不会阻止不参与协议的写入者。

新增 `origin_storage_coordination` 平台接口。Web 在整个重新读取、校验、转换与单文档写入期间持锁；占用时立即拒绝，缺少安全上下文或协调能力时拒绝写入，未提供无锁降级。用户 aggregate、replay 文档和按 owner 分开的 Care 文档使用不同锁名。Care 锁覆盖服务的整个修改过程；直接调用底层 store.write 的非参与写入者不在保证内。原生分支只协调当前进程，不宣称跨进程事务。

Web 偏好写入另外检查已加载档案或选择的内容指纹。其他页面的 storage 事件不读取载荷，直接使 AppState 的偏好、草稿、Care 预览与派生结果失效；根界面要求用户显式重载。未保存编辑会被放弃，平台已接收的写入仍可能完成。原始记录不因事件被清空。

## 实际浏览器复测

新候选 release 探针使用本机 `8964` 来源，旧操作和预期保留。两个页面新增后保留 A、B；第二个陈旧修改被拒绝，首个修改与三条历史保留。用原写入故障注入接口暂停持锁页面，另一页面被拒绝且展示的记录/历史未变；释放后重试保留四条记录和五条历史。

两个页面冻结空 Care 文档的同一恢复预览；首个恢复成功，第二个被判为陈旧。实际读取的完整 Care JSON 与 W09 事先冻结的原始 JSON 相同，覆盖观察、问题、药品讨论、会后结果、自查、提示和反馈七类内容。这里使用固定合成 owner 与授权谓词，不替代实际登录会话验收。

只暂停本轮自建本机服务器后，已加载页面的新修改仍保存成功。关闭两个页面后新建页面，四条记录、六条历史与完整 Care JSON 均读回。此操作是页面重新创建，不是浏览器进程终止、操作系统重启或浏览器全局断网。

单独 `8965` 来源保留原记录后进行实际容量压力：存入 5,240,080 字符的合成内容，六级大小均出现容量拒绝。新增 B 被拒绝，显示的原 A 身份、备注与历史 ID 前后一致。压力键保留，不删除其他来源的数据。此比较未读取完整 aggregate 原始字节，不能把摘要相等称为完整原始文档相等。

浏览器原始观测和独立完整 Care/记录核对单独保存。探针入口不是 `lib/main.dart`；正式入口的失效界面、当前完整候选旅程、其他浏览器、缺少 Web Locks 的实际环境与物理终止仍需各自检查。
