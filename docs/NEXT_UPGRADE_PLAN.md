## 1. 推荐方向

下一轮以 **“可持续记录、可解释回放、可复现试用”** 为主题。三个方向共享一组输入场景、产品流程与验收证据；每个里程碑都同时交付用户可见改进、可执行验证和可展示结果。

建议把下一次功能版本暂称为 **v0.3 候选**，版本号与日期在范围收敛后确定。前置的基线与依赖修复可以单独形成维护版本，不必等待整轮功能完成。

核心旅程：

> 从历史餐创建新草稿 → 确认时间与份量 → 保存 → 查看来源、缺失信息及解释 → 在合成场景中回放 → 整理并交付所选记录。

完整恢复功能放在下一阶段，先解决身份隐私、数据范围和事务边界。模型研究继续保持 `trace_only`，研究产物不自动获得推荐决策权限。

## 4. 分阶段交付

### M0 — 基线与升级通道

交付内容：

1. 复核当前 registry/root/trace 对应关系，去除 63 的硬编码依赖；验证数量、身份集合、重复和遗漏，不能仅改成另一个固定数字。
2. 刷新受影响的报告与过时队列描述。兼容性通过不改变完整闭包 HOLD。
3. 将依赖更新分成 npm 安全补丁、Dart 兼容升级、重大版本升级，避免混合批次；每批审阅后更新绑定的锁文件身份并跑相关检查。
4. 核对旧 issue 的原始验收要求，形成已覆盖/部分覆盖/仍待做清单；本规划不关闭 issue 或合并 PR。

验收：新增/移除/重复 root 的负例有效；当前版本报告可以重建；目标依赖 PR 检查通过且没有绕过身份门禁；主分支原有通过状态可追溯。

### M1 — 一份餐食的完整流程（首个功能里程碑）

产品交付：历史餐复用成新草稿、恢复草稿、来源绑定份量预览，以及结果旁简洁的“依据与缺失信息”入口。复用现有解释树和 trace 数据，避免再维护第二套说明逻辑。

研究交付：围绕同一组场景写明输入、独立预期、允许误差或精确比较规则、实际结果与限制；按用户旅程选择需要补充的执行覆盖，不追求 descriptor 数量增长。

展示交付：在独立合成数据环境验证 release Web 旅程，提供约 90 秒演示脚本、截图与可重跑步骤。先完成本地可运行版本，再决定公开托管形态。

共同场景：

| 场景 | 用户操作 | 算法/数据断言 | 演示要点 |
| --- | --- | --- | --- |
| S1 常用餐 | 复用前一次餐食，调整时间和数量并保存 | 新旧记录隔离；份量换算绑定相同来源；结果按新输入重算 | 展示从复用到解释的完整流程 |
| S2 信息不完整 | 录入缺营养项或不支持份量来源的食物 | unknown 不变成 0；不支持的投影明确 withheld；用户能看懂原因 | 展示系统何时保留未知 |
| S3 中断与修改 | 离开页面、恢复草稿、保存后再次编辑 | 不重复保存；旧预览和旧结果失效；账户切换不泄漏草稿 | 展示日常可靠性 |

验收：三组场景在所声明平台通过；采集现状与改进后的操作步骤和任务完成时间，不先宣称效率提升；中文/英文、大字号、键盘焦点及窄屏关键流程可完成。合成测试不替代实际参与者的易用性观察。

首个可实施切片：**来源绑定份量预览 → 一个独立数值案例与一个缺失案例 → 同 revision 的合成流程演示**。该切片改动较集中，三条目标都能产生可审阅结果；随后接历史餐复用与草稿。

### M2 — 一周记录可交付、可恢复

1. 将已有访前整理与日志交付串成一个选择—预览—交付流程；复用当前 HTML/PDF 管线。优先保证 HTML/可选取文本、阅读顺序、中文分页和实际分享行为，单独列出图像 PDF 的限制。
2. 先确定 portable package 的完整范围：当前 v4 含观察记录，但 care workspace 的讨论、会后结果、自查不在备份内。缺失内容必须列明，不能展示“完整备份”。
3. 完成包级身份隐私投影设计后，先实现单平台、同 owner 的显式确认恢复；跨设备、账号合并与云同步单独排期。
4. 持久导入须有事务、去重、冲突预览、旧状态回滚及崩溃恢复验证；提醒恢复不自动获得目标设备通知权限或激活能力。

验收：当前状态→导出→独立测试状态恢复的语义一致性通过；故障注入后保持原状态或可确定恢复；未知字段/未知版本拒绝写入；观察的缺失值、来源和时间信息保持；源记录修改会使旧预览失效。现有 hash 只证明内部一致性，不宣称加密或发行者认证。

### M3 — 真机、独立复核与发布验收

日常线：先选择一个主要移动平台，实测离线重启、长时间线、大字号和系统分享；提醒继续承接现有三个 `in_progress` 项，分别核对权限、可见送达、点击/冷启动、时区与重启行为。模拟器排程登记不能替代真实送达。

研究线：为一个明确用途和一组固定问题准备独立复核包；逐项记录不确定性、人因、科学验证、模型资格与独立审查所需的新证据。外部参与者或专家尚未安排，不承诺这些证据会在同一开发周期全部完成。

发布线：按精确 commit 关联适用的产物摘要、校验值、许可证/NOTICE、SBOM、合成旅程、截图来源与 CI；明确区分 source、metadata package、可运行 app 和开发研究工具。

验收：只列实际通过的设备、系统、构建和场景；发布材料能定位到对应证据；不支持的能力继续显示具体限制。

## 5. 本轮研究方向如何产生实质增量

- **输入质量对输出的影响**：固定合成场景，分别扰动份量、营养缺失、来源状态及时间上下文；测量数值变化、解释变化和 withheld 行为。复用既有敏感性工具，新增价值是对真实产品路径的绑定和独立预期。
- **结果来源可追溯性**：优先追踪 S1–S3 的实际生产路径及其依赖；明确哪些边有证据、哪些仍未解析。修复 registry 漂移后再逐步扩大范围，完整闭包作为单独研究项目保留。
- **解释是否被理解**：用相同合成任务开展形成性易用性观察，记录参与者能否区分缺失值、trace 和建议，以及能否找到来源。预先写定问题与记录方法；小样本观察只用于改进体验。

M1 后优先选择两个具体算法切片：其一，扩展已有 replay capsule 的异常与迁移语料，覆盖损坏包、未来 schema、重复 JSON 成员、深度/大小上限及跨运行时差异；其二，为已有 evidence-currency gate 增加离线候选变更对比和跨会话回执留存，让历史结果继续引用当时的证据快照。前者复用现有回放能力，后者复用现有过期阻断与 receipt；两者都不新建并行规则引擎，也不将联网更新自动应用到运行时判定。

以上分别提供数值、工程和人因证据；不能互相代替，也不能由内部测试推导临床有效性。

## 6. 范围与排期原则

- 每个迭代包含一个用户可见变化、一组相关验证、一份可展示证据，优先完成 M1 后再展开多个大模块。
- 当前功能版本不要求同时完成云端照护共享、通用 FHIR/CQL 接入、个体化药时/剂量优化、所有平台分发或完整依赖闭包。
- 真实数据试点、完整备份恢复与模型权限升级分别需要其具体设计和证据；不作为短期演示的隐含承诺。
- 时间按里程碑与验收安排。本提案没有掌握可投入工时、目标真机和独立审阅资源，因此不作上线日期承诺。
