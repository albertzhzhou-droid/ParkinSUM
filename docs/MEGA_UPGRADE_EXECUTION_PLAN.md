## 1. 这次升级要达到什么

2026-09-30 后续执行已接纳 W15 多产品 SPL：先冻结独立的 8 产品预期，实测旧导入器，再实现产品归属并核对完整公开响应；另修复冲突检查的旧缓存回退与失效边界。来源和反例见 [W15 研究记录](SPL_PRODUCT_SCOPING_RESEARCH_2026-09-30.md)。当前候选完整回归、发布旅程及 W13 剩余测量仍待最终绑定；接纳包数现为 17，其他 18 包继续保留，未声称原 35 包全部完成。

将 ParkinSUM 从现有的记录与研究工作台，推进为 **可连续记录、可靠恢复、解释来源差异、可公开复现的完整应用候选版**。

本计划包含 **35 个工作包：17 个核心优先包、18 个扩展包**。全储备粗估约 **90–160 个代理工作小时**，其中核心优先池约 37–65 个代理工作小时；这是多个执行窗口的可选工作储备，不能解释成一个 12–18 小时窗口会全部完成。多个代理并行也不会使有依赖的工作自动消失。

首窗口的交付目标：

1. 接收并验证当前已经在做的录餐、恢复、导入器、规则输入和回放工作。
2. 至少争取完成一组相互连通的产品增量：Insights 数据质量与回看、Timeline 筛选、Care 到交付流程；按实际进度选择完整子集。
3. 完成一条来源研究链：公开来源小语料 → 独立预期 → 重复证据裁决 → 一致候选快照。数据库未释放时先做不冲突的语料与独立验证。
4. 至少交付一个有明确问题、参数域、独立检查与反例的算法实验；默认选高精度域扩展或启发式敏感性，避免只增加登记表。
5. 形成一个通过当前源码身份验收的本地 release Web 候选、完整测试记录、公开合成旅程和后续清单。公开托管、远端提交与发布沿用执行时已有授权。

**时间用于安排工作，不是质量指标。** T+10 小时是检查点，不是停止点。若仍有已授权且前置条件满足的高价值工作，继续推进；不通过等待、重复已通过测试、盲目扩功能来凑时长。工具和会话限制可能影响实际连续运行，因此必须留下可恢复状态。

### 4.3 依赖与选择规则

- `depends_on` 是硬前置；不得用“预计会完成”绕过。
- `conditionally_recheck_after` 表示：该包若纳入当前候选且发生变化，相关 QA 证据要重新检查；它不是第二组实现前置。
- 实际声明的输入指纹始终决定证据是否失效；条件重验列表只是非穷尽提示，不能因某个变化未列入就复用旧结果。W13 优化产品代码后必须重走受影响的 W31 旅程并重新测量；后续产品、存储或工具链变化也会使相应性能结果失效。
- W17 的独立语料先于 W14 的新裁决实现，避免用生产输出反过来生成标准答案。
- W16 需要 W08 的存储契约稳定，不能与另一个 agent 并发改相同数据库文件。
- W31/W34 验收本窗口实际接纳的增量。未选择或未完成的核心包保留后续，不把“优先池未清空”伪装成所有功能完成。
- 单个包过大时按能够单独验收的接口/行为切片；更新本规划中的剩余范围，不能仅因为写了一部分代码就修改权威队列为 shipped。

## 5. 各方向的设计与验收重点

### 5.1 产品体验与数据质量

**Insights：先定义数据，再绘图。** 当前 `ProteinTrendPoint` 只有 time 和 double protein，页面只对日期设下界。升级应区分真实零、未知、已记录餐数、已知营养餐数和计算分母；使用明确时区及双边时间范围，单列未来时间异常。支持自选日期、筛选、点击回原记录，不把记录缺失解释成行为缺失。

**Timeline/目录：在已有基础上增加检索与回看。** 保留现有虚拟列表与近邻关系；筛选只改变视图。目录先建立别名、来源、辖区、revision 变化的查询基准，再对实测热点使用缓存或索引；版本变化必须使缓存失效。

**Care 到交付：一个明确选择流程。** 用户选择日期、记录和问题，预览内容及删敏项，再用既有交付能力输出。来源或 owner 变化必须使旧预览失效。HTML 的语言和阅读顺序、长文分页、字体失败与分享取消优先收口；可搜索 PDF 是独立增量，不能把 raster PDF 包装成语义可访问 PDF。

**恢复：先证明当前范围，再扩大。** 第一窗口重点是真实存储验收现有有限恢复。观察/Care 的多存储事务、加密备份、跨设备恢复分别需要契约设计，不通过“先写一半再补另一半”实现。hash 不是加密、签名或真实性认证。不得在用户真实数据上演练故障恢复。

### 5.2 算法与研究

主问题：**来源差异如何影响输入、参数、结果和解释，软件如何证明没有掩盖这种差异。**

1. 公开来源小语料采用可合法获取的最小必要片段。候选目标为约 12–20 个样例，覆盖完整、缺失、LOQ、修订与多产品；数量不是通过标准。每个预期应能定位原始字段，由独立推导或实现给出。
2. 重复营养观察先判断来源、方法、单位、范围与版本可比较性。输入重排不得改变已确定的选择；不能把不同方法或有冲突的测量强行平均。
3. 多产品 SPL 按产品分离成分、强度、route/form 和编号。不能把同一文件中另一产品的信息拼到当前产品。
4. 一致性快照以完整旧版、完整新版或明确重试/HOLD 为合法结果，不能让一次候选集混合两个目录版本。
5. 份量/匹配不确定性只枚举有来源的合法组合。现有 protein/fiber 联合枚举继续复用；无来源概率不制造概率或临床置信度。
6. 启发式参数实验固定探索域，报告排序翻转、并列和阈值跃迁；不自动调整生产权重。
7. 数值验证扩展已有独立高精度参考的参数域、极限与退化情景。可辨识性实验使用明确的 synthetic manufactured data，保留失败拟合、宽区间和等价参数组，不能解除临床校准限制。
8. 关系测试关注新增检错贡献、误报、等价/不可达变异和未见 seed。局部依赖图只承诺选定三个 result sink、声明语言子集与未解析边，不宣称全项目完整闭包。
9. 时区实验区分 UTC instant、原始 civil intent、gap/fold 和规则版本；历史缺失信息不得回填猜测。
10. currency 回执保留历史 snapshot。联网获取进入候选审阅，不自动替换运行时证据或取消过期阻断。

每个研究包必须有：明确问题、输入域、独立预期或比较、可复现 seed/配置、失败/反例和结论边界。参考了论文或增加来源数量本身不是研究交付。

### 5.3 工程、验证与发布

- 扩展现有 `run_verify_all.mjs`，不新造平行门禁。超时、中断、缺工具和缺报告都必须显式失败或未执行；每个 gate 完成就留下检查点。
- 依赖按小批次审阅。开发依赖与生产依赖告警分开；隐私契约 digest 刷新前必须检查实际能力变化。
- CI 分层保留既有受保护检查身份和必需覆盖。减少重复整套测试不能意味着遗漏 gate、golden 或负例。
- 延续当前 `generate_upgrade_delivery_index.mjs`，绑定源码、未提交内容、锁文件、构建参数、工具、fixture 和报告；旧检查不能仅靠替换 hash 变为有效。
- 发布版 Web 必须通过正式入口、独立服务与隔离浏览器存储完成记录、修改、关闭重开、恢复和报告，不能用进程内 ephemeral 仓库代替。
- 性能使用 100/1,000/10,000 条合成记录的固定数据；先测基线再定阈值，选最多两个热点优化。记录硬件、浏览器、artifact、重复次数和分布；能耗与真机体验未测时保留未验证。
- Android/Apple 升级先核验当前源码和执行时官方兼容资料，再决定必要变更。大版本迁移不能和最终发布修复混在一批。

## 6. 并行规则：四个执行位，明确单写者

| 角色 | 可自主推进 | 必须串行的共享点 |
| --- | --- | --- |
| 主协调/整合 | 基线、调度、跨包接口、接收变更、回归结论 | `app_state.dart`、`services.dart`、共享数据库/恢复协议、导航、schema catalog、registry、allowlist、队列、时间线 |
| 产品 agent | 独立 projection/service、组件、页面专属测试与文案 | 修改共享状态、统一 i18n、schema 或数据库前交给整合者接线 |
| 研究 agent | 独立语料、oracle、研究 runner、局部算法测试 | importer/候选投影/probe/配置同一时间各只有一个 owner；最后统一绑定身份 |
| 工程/QA agent | runner、依赖候选、构建、产物及性能测试 | lockfiles/workflows 明确唯一 owner；Flutter/Gradle/Xcode、设备及同一 build 输出独占运行 |

所有 agent 共享文件系统；目录不同不等于隔离。其他 agent 先实现独立模块与测试，再由单写者接共享文件，不以“后面合并”解决同时写文件冲突。

- 不创建完整仓库副本或迭代备份目录，遵守现有 `AGENTS.md` 的原地迭代要求。
- 不覆盖当前活跃 chat 的修改。尚未交接时选择语料、独立模块、只读审查等不相交工作。
- 不自行向其他用户 chat 发消息或中断它；只有得到用户明确授权后才用跨 chat 协调工具。子 agent 间按本任务文件所有权表协调。
- git commit、PR、远端发布按执行时已有用户授权处理；本规划不新建授权。未提交源码本身可以验收，但报告必须绑定完整 dirty fingerprint。

## 7. 长跑检查点与恢复协议

规划工作包表中的状态全部是 `proposed`，不是当前实现结论。真正执行时在已忽略的 `build/mega_upgrade/run_state.json` 保存运行状态，至少包含：

- run ID、启动时间、当前阶段、选中包与未选中包；
- HEAD/public-main、dirty 文件内容指纹、关键 schema/配置/依赖身份；
- 每个包的 owner、实际修改文件、依赖、当前状态和下一动作；
- 针对性验证的命令/工具、退出码、报告位置和绑定身份；
- 已知失败分类、不能复用的旧结果、剩余跨包接口；
- 下一次可安全恢复的位置，以及最终 QA 是否已开始。

状态建议为 `proposed → ready → implementing → verification → verified_local`，另设 `blocked_environment`、`external_evidence_required` 和 `deferred`。不要将 `verified_local` 自动转换为 shipped。

每完成一个实现迭代：

1. 验收实际行为，记录相关验证；只有输入或未解决问题变化时才扩展/重复测试。
2. 在唯一的 `docs/APP_EVOLUTION_TIMELINE.md` 追加一条记录，包括基线、变更、schema、验证、限制与局部回退范围。
3. 更新运行检查点，立即选择下一个前置已满足的工作包。
4. 不以一个工作包完成、一个 agent 返回或一轮测试通过作为整个任务结束条件。

建议在 T+0、2、4、7、10h 和最终验收前额外检查一次。会话压缩或工具中断后先读检查点并核对文件身份；未结束的命令/子进程先检查状态，不能盲目重复启动。

检查点是恢复元数据，不是第二本项目时间线。不得把私人导出、凭据或大规模原始日志复制进去。

## 8. 遇到问题时继续推进的规则

| 问题 | 处理 | 后续工作 |
| --- | --- | --- |
| 本包功能/断言失败 | 修复所属包并保留最小反例；不降低验收 | 其他不依赖本包的 agent 继续 |
| 源码或依赖身份变化 | 将关联旧证据标为失效，重新跑受影响检查 | 不靠手动改 digest“通过” |
| 环境、下载、驱动失败 | 记录精确失败，做有界排查，换已支持目标或离线语料 | 不把环境失败写成产品通过；转可做包 |
| 并发文件冲突 | 停止写相同文件，重新读取、交由唯一 owner 接收 | 做独立语料/模块，不重置别人的改动 |
| 包过大、可能侵占 QA | 完成可独立验收的子片，其余 deferred | 收缩当前版本范围，不交付半写入状态 |
| 需要真实人因、母语评审、真机、真实校准 | 完成协议/工具/合成准备，保留外部待验 | 转其他可自主包，不用模拟结果替代 |
| 权限/用户输入是该动作的必要条件 | 把具体可审阅结果准备好，准确说明待决事项 | 不依赖该条件的工作继续 |
| 预算或会话限制 | 保存状态、当前证据和下一可执行动作 | 不能把中断写成项目已全部完成 |

排查不应无限重复相同失败。默认同类失败经过两轮有实质变化的尝试仍无进展，就保存证据并切换工作包；这只是调度规则，不表示放弃最终解决。

## 9. 最终验收与交付定义

只有实际纳入候选的功能计入最终范围。最终至少包含：

- 修改范围与共享配置稳定，相关格式/静态检查通过。
- 功能相关单元、状态、迁移及交互验证；对于数值/导入研究使用独立预期与反例。
- 当前候选的完整 Flutter 回归及必需 Node/组合门禁；明确未运行、失败、环境受阻项。
- 同一源码身份的 release Web 构建、真实存储旅程、窄屏/键盘/大字号检查；可用平台上的必要构建。
- 性能基线及实际优化对照，不能把 debug 初始化时间当 release 性能结论。
- public/privacy/license/release 门禁及交付索引；科学/人因/独立审核/真机 HOLD 仍按实际证据保留。
- 一份面向用户的改进清单、一份研究结果摘要、可查看的本地应用/演示产物，以及可恢复的后续工作包状态。

全套检查通过后不无理由重复跑。若最终 QA 后代码或配置再次改变，重新运行受影响验证，并按影响范围判断完整回归是否需要再做。

公开材料仅使用隔离合成数据。发布软件、安装到用户设备、外部消息或远端变更按执行时的授权处理；不把这份规划误解为已经做过这些动作。

## 10. 进一步扩展，但不强塞进首窗口

这些可以排入以后窗口，先满足具体前置条件：

| 方向 | 可自主完成的部分 | 需要另外满足的条件 |
| --- | --- | --- |
| 加密备份与恢复 | 威胁模型、格式/版本设计、成熟加密库的原型、合成故障演练 | 密钥恢复策略、平台保护、迁移与安全审查；不自制密码学 |
| 拍照/OCR/语音辅助录入 | 以合成或明确许可数据验证“提取→用户确认→普通录入” | 模型/服务选择、资源成本、隐私与用户确认；不自动解释药量 |
| 传感器/动作研究沙盒 | 开放且许可明确的数据解析、可复现实验及误差报告 | 数据权利、测量效度、独立评审；不作为诊断 |
| 多端照护协作 | 本地角色与同意模型、冲突协议、接口模拟 | 身份、服务器权威、撤回/删除、后端运维和真实角色授权 |
| 通用互操作 | 针对明确 profile 的离线 fixture 和差异检查 | 权威术语、真实系统接入和独立一致性验证 |
| 临床校准与人因研究 | 协议、测量表、分析代码和独立审阅包 | 合格数据、参与者/专家、实际批准与执行；不由 Codex 伪造 |

这些方向的价值取决于证据和项目用途，不以“可添加功能数量”作为升级成绩。
